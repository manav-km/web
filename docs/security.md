# Security notes

**Identity**: Firebase only. Every protected route verifies the ID token (signature, expiry, revocation). Admin = verified custom claim. Nothing from the request body/localStorage is trusted.
**Authorization**: `require_admin` on every admin/security route; conversation/request ownership checked per object; failures are logged as security events.
**Admin page**: `/portfolio/admin` is a static shell with no data. The UI is only built after the backend says the user is admin, otherwise the browser is sent to `/`. (A static host can't server-side-render a 403; the real guarantee is that every admin API call is rejected without the claim. Verified by `backend/tests/test_authz.py`.)
**Abuse & Rate Limiting**: atomic Postgres rate limiter (`check_and_increment_rate_limit`) per HMAC-hashed IP+endpoint. Plaintext IPs are never stored in `rate_limit_blocks` (hashed with `IP_HASH_SALT`). Temporary blocks, events written to both Audit Log and Security View.
**IP Data Protection & Retention**: client IPs in `audit_logs` and `security_events` are automatically masked to `[masked]` after `IP_RETENTION_DAYS` (default: 90 days) via daily cron (`/api/v1/admin/cron/mask-ips`). GDPR-style data export (`GET /api/v1/profile/export`) and self-service account deletion (`DELETE /api/v1/profile/account`) are available in the account dropdown menu.
**HTTPS & Transport Security**: backend redirects insecure requests with 308 when `ENFORCE_HTTPS=true` and `X-Forwarded-Proto=http`. Strict-Transport-Security (HSTS) with max-age 2 years and preload is returned on responses. Frontend includes `js/core/https.js` and CSP enforces `upgrade-insecure-requests`.
**Headers/CSP**: root `cloud-run.json` strict CSP: `upgrade-insecure-requests`, no inline scripts/styles; Google Analytics 4 allowed with consent; only Firebase + Supabase + your API allowed. API adds nosniff, frame-ancestors none, and `no-store` on private endpoints (`/api/v1/profile`, `/api/v1/admin`, `/api/v1/messages`, `/api/v1/connect`, etc.).
**Static Assets**: the `assets/` directory at the repository root (`achievements/`, `blog/`, `profile/`, `projects/`, `uploads/`) is web-servable once deployed; these contain public portfolio and demonstration media only.
**XSS**: all dynamic content inserted with `textContent`; URLs restricted to http(s); blog bodies render as plain paragraphs.
**Uploads**: images only (PNG/JPEG/WebP, 2 MB), server-generated filenames, signed one-time URLs.
**Secrets**: env vars only. `.env` is git-ignored. The GitHub token lives only on the backend (`GITHUB_TOKEN`).
**Realtime**: chat (conversations + messages) now lives in Firebase RTDB, written only by FastAPI via the Admin SDK — `.write: false` in `firebase/database.rules.json` blocks direct client writes to both paths, so the authorization/rate-limiting/audit-logging FastAPI already did for Supabase-backed messages still applies unchanged. Reads are scoped to a conversation's `participants` map. Drafts/typing/presence ARE written directly by the client (low-stakes, high-frequency) under rules requiring `auth.uid === $uid` plus conversation membership. Presence reads are scoped to users sharing conversations or self. `/unread/{uid}/{convId}` can only be zeroed by its owner, never incremented or touched for another uid — closes the "fake your own unread state" concern in the rules themselves. A separate `/signals/{uid}` ping (timestamp + event type only) covers non-chat notifications (status changes, reviews). See `docs/architecture.md` §13b-c and `docs/firebase.md`.
**AI checklist**: generated tasks are validated (category against the enum, weight clamped 1-10, title length-capped) before insertion — same "untrusted generated content" treatment as the AI overview. The AI can only ever create `source='ai'` tasks; it never sets `status='completed'` or writes a completion percentage — that's computed from real task state in `db/tasks.py`, never cached. Regeneration is preview-then-confirm (`/checklist/regenerate-preview` writes nothing; `/checklist/regenerate-apply` requires the admin's explicit payload) so an AI pass can never silently overwrite completed or manually-edited work — see `docs/architecture.md` §13c.

## Known gaps (be aware)
- No CAPTCHA/bot challenge yet (Cloudflare Turnstile is the suggested addition on `/connect` and sign-up).
- Firebase sign-up/sign-in happen directly against Firebase, so brute-force protection there is Firebase's own; the backend limiter covers the backend endpoints.
- Email verification is *sent* on sign-up but not yet *required* to submit the Connect form.
- Audit "Name of performer" shows the UID/name captured server-side; profile names appear once a user fills the form.
- Audit-log inserts are best-effort: on a database error they go to server logs instead of failing the request.
- The frontend doesn't yet have the RTDB client-side listeners (conversations/messages/typing/presence) or the mobile-responsive pass — both are backend-complete, frontend-pending. The CSP also needs a `connect-src`/`wss:` addition for the RTDB domain once that frontend work lands.
